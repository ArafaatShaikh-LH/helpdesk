# Forward an email from a ticket

## Agent steps

1. Open a ticket and find the email to forward.
2. Open that email's three-dot menu and select **Forward**.
3. Check **From**, enter the new **To** recipients, and optionally add Cc, Bcc or a message.
4. Review the selected email and its checked attachments. Uncheck any attachments you do not want to send.
5. Select **Send forward**. A confirmation means it has entered the email queue, not that delivery has completed.

To, Cc and Bcc start empty every time. The selected message body (including any older quotations already inside that message) is forwarded. Other ticket messages and internal comments are not added. The original recipients are not copied into the new envelope or the generated forwarded-message header. Agent notes are plain text.

The sending mailbox uses the existing reply policy: the ticket's latest incoming mailbox is locked when receiving-mailbox routing is enabled; a ticket without a known receiving mailbox requires an explicit business mailbox choice. No Reply is excluded. A mailbox change while the window is open blocks sending until the agent reopens it.

Replies to the forward use that business mailbox and join the same ticket through the new outgoing message's Message-ID. This requires the mailbox's existing inbound processing to be working. No email to the original customer is generated by the forward endpoint or by receiving its reply. Normal ticket notification rules remain independent.

**This is a shared ticket conversation, not a private side conversation. Everyone who can read the ticket may be able to read the forward and the reply.** Agents should inspect To/Cc/Bcc before any later Reply or Reply All.

## Behaviour and permissions

- Agents need ticket read permission to prepare a forward and ticket write permission to send it. Portal users and guests cannot call either operation.
- Only an Email Communication directly linked to the requested ticket is accepted. Another ticket's email, internal comments, unrelated files and ticket-level attachments are rejected.
- All files directly attached to the selected email are selected by default. Their original file records are preserved; the outgoing message receives additional links with the original privacy setting. This first version does not upload additional files in the forward window.
- The selected email body is sanitized. Private local images that are not among the selected attachments cannot be embedded. Original To/Cc/Bcc headers are not inserted into the generated quote.
- A new Communication is saved with the explicit recipients, chosen business sender, `Fwd:` subject, source link and a new Message-ID. Original thread headers are not reused.
- Forwards do not set first-response timestamps, update last-agent-response timestamps, or apply the automatic agent-reply status transition. A later incoming reply follows normal inbound ticket behaviour.
- Outbound mute, disabled agent emailing, disabled mailboxes and tickets with the email workflow disabled are respected. The endpoint fails instead of silently recording an unsent forward.
- The modal has a separate in-memory draft. It never reads or overwrites the regular reply draft, recipients or remembered sender. Closing discards this forward draft. Failed sends keep the window and draft open.
- Retrying an identical request from the same window returns the existing Communication instead of queueing a second copy. The deterministic name includes ticket, source, acting user, request ID and payload. Concurrent duplicate inserts fail safely under the database primary key; no second mail is queued.

## API contract

Existing authenticated Frappe `run_doc_method` transport is used; no new public guest API is introduced.

### Prepare

`POST /api/method/run_doc_method`

```json
{
  "dt": "HD Ticket",
  "dn": "123",
  "method": "get_forward_email",
  "args": {"communication": "selected-communication"}
}
```

Returns `communication`, `source_modified`, prefixed `subject`, original `sender`, plain `preview_text`, and attachment metadata (`name`, `file_name`, `file_url`, `is_private`). It never returns original Cc/Bcc for prefilling. Sender policy continues to come from `get_reply_sender`.

### Send (POST only)

```json
{
  "dt": "HD Ticket",
  "dn": "123",
  "method": "forward_email",
  "args": {
    "communication": "selected-communication",
    "source_modified": "2026-11-02 12:00:00.000000",
    "request_id": "generated-uuid-for-this-draft",
    "to": "recipient@example.invalid",
    "cc": "",
    "bcc": "",
    "note": "Please review the attached document.",
    "from_email": {"email_account": "Contracts", "email_id": "contracts@example.invalid"},
    "attachments": ["source-file-id"]
  }
}
```

Returns the queued Communication name. `attachments: []` excludes all attachments; omitted attachments means all source files. To is mandatory. Recipient fields accept comma-separated addresses or display names and reject newlines, invalid tokens and more than 50 total recipients. Notes are limited to 50,000 characters. A source modified since preparation must be reviewed again. No client-supplied source body, arbitrary file URLs or alternate ticket reference is accepted.

The request transaction owns the new Communication, attachment links and Email Queue record. Failure before queue creation raises an error so Frappe rolls back the request. No commits or immediate SMTP sends occur inside the endpoint.

## Installation and rollback

Deploy this Helpdesk fork on the existing compatible stable branch and run the site's normal migration. The additive patch creates hidden, read-only `Communication.custom_hd_forward_source` (Link to Communication). Fresh installs receive the same field through `get_custom_fields()`. Existing Communications and mail settings are not changed.

Do not disable outbound email, invitations or incoming email during this deployment. Normal hosting migration may briefly put the site into maintenance. Deploying only frontend assets without the migration is unsupported; sends fail with an explicit update-required error when the field is absent.

Rollback should retain both the custom field and the small `on_communication_update` guard, even if the menu/dialog are removed. Delivery updates to existing forwards must continue to be excluded from customer-response SLA calculations. Do not delete existing forward Communications or original attachments.

## Validation and release check

Local isolated backend checks exercise the production forwarding functions with mocked persistence and email queuing. Local Vue checks compile both changed components and exercise the dialog with mocked Frappe resources. These checks do not prove live SMTP delivery or live inbound matching.

The integration suite lives at `helpdesk.helpdesk.doctype.hd_ticket.test_forward_email`. Run against a disposable Frappe test site after migration:

```sh
bench --site TEST_SITE run-tests --app helpdesk --module helpdesk.helpdesk.doctype.hd_ticket.test_forward_email
bench --site TEST_SITE run-tests --app helpdesk --module helpdesk.helpdesk.doctype.hd_ticket.test_reply_sender
```

Before release, build the complete frontend against the site's compatible Framework UI dependency. After deployment, use a clearly labelled synthetic ticket for one separately approved internal email test: forward to an internal recipient, confirm the From mailbox and attachment, reply from that recipient, and verify the reply returns to the same ticket without emailing the original customer. Confirm the regular reply draft and first-response/status fields are unchanged by the forward.
